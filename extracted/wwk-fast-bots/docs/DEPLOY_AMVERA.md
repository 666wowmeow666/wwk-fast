# Деплой WWK FAST BOTS на Amvera

Проект собирается через обычный Dockerfile. Конфигурация `amvera.yml` задаёт `containerPort: 8080` и `/data` как точку постоянного хранилища. Приложение хранит бизнес-состояние в PostgreSQL; папка `/data` сейчас не используется для локальной базы. Amvera поддерживает Dockerfile без docker-compose и принимает `amvera.yml` для уточнения параметров запуска.

## 1. Создать PostgreSQL

1. В Amvera на главной странице откройте **PostgreSQL → Создать базу данных**.
2. Задайте имя базы, имя отдельного пользователя и пароль. Имя базы и пользователя `postgres` зарезервированы. Для стабильной работы документация Amvera рекомендует тариф не ниже «Начальный».
3. После запуска кластера откройте его страницу «Инфо» и скопируйте внутренний адрес для чтения/записи вида `amvera-<username>-cnpg-<project_name>-rw`.
4. Соберите `DATABASE_URL` по шаблону:

   `postgresql://<db_user>:<db_password>@<internal_host>:5432/<db_name>`

   Для подключения к базе через внешний домен добавьте `?sslmode=require`. Приложение преобразует `postgresql://` в `postgresql+asyncpg://` и `sslmode` в параметр `ssl` для asyncpg. Не публикуйте эту строку: пароль БД — секрет.

## 2. Создать приложение

1. Создайте в Amvera проект типа **Приложение**.
2. Выберите окружение **Docker**. В репозитории уже находятся `Dockerfile` и `amvera.yml`; дополнительный `docker-compose.yml` не нужен и Amvera его не поддерживает.
3. Подключите репозиторий с исходниками. Для приватного GitHub-репозитория в разделе «Репозиторий» выберите GitHub, добавьте GitHub access token, выберите репозиторий и ветку, затем настройте webhook на событие `push`. В инструкции Amvera описан и вариант через их репозиторий с синхронизацией по webhook.
4. Ветка для развёртывания — та, в которую попадёт проверенная сборка (например, `main`).

## 3. Переменные окружения

В панели проекта → **Переменные** добавьте значения. Секреты отмечайте секретными.

Обязательные для первого запуска в mock-режиме:

- `CLIENT_BOT_TOKEN` — токен клиентского бота от @BotFather;
- `TEAM_BOT_TOKEN` — токен внутреннего бота от @BotFather;
- `ADMIN_TELEGRAM_IDS` — ваш Telegram ID;
- `DATABASE_URL` — строка PostgreSQL из шага 1;
- `CRM_MODE=mock`.

Рекомендуемые настройки безопасности перед допуском внешних клиентов:

- `CLIENT_REQUIRE_MANAGER_APPROVAL=1` — менеджер подтверждает каждую новую привязку организации;
- `CLIENT_VISIBLE_DOC_GROUPS` оставить пустой, пока вы лично не проверите группы документов и не убедитесь, что среди них нет внутренней маржи/расчётов.

Для подключения реальной 4logist позже добавьте `CRM_MODE=real`, `CRM_CLIENT_ID`, `CRM_CLIENT_SECRET`, `CRM_USERNAME`, `CRM_PASSWORD`. Access/refresh token приложение получает самостоятельно. Не отправляйте их в чат и не добавляйте в GitHub.

Остальные параметры и дефолты находятся в `.env.example`.

## 4. Первый запуск

1. Запустите сборку. При старте `RUN_MIGRATIONS=1` применит Alembic-миграции к PostgreSQL, затем поднимутся боты и health endpoint.
2. Проверьте логи: `Миграции применены`, `Бот team запущен`, `Бот client запущен`.
3. Проверьте `GET /healthz` на домене приложения: должен вернуться JSON с `status` и состоянием ботов.
4. Откройте внутренний бот и отправьте `/start`. Администратор из `ADMIN_TELEGRAM_IDS` автоматически получит роль ADMIN.
5. Добавляйте сотрудников командой `/addstaff <tg_id> <ROLE[,ROLE]> <ФИО>`. Доступные роли: `ADMIN`, `MANAGER`, `LOGISTICIAN`.
6. Проверьте клиентский бот в `CRM_MODE=mock`: заказ `WWK-0001`, последние 4 цифры ИНН `0001`. Бот должен явно показывать, что это тестовые данные.

## 5. Подключение и проверка 4logist

1. Убедитесь, что для интеграции выданы `Client ID`, `Client Secret`, логин пользователя и пароль пользователя 4logist.
2. Заполните четыре OAuth-переменные и измените `CRM_MODE` на `real`. Приложение выполнит password grant, сохранит access/refresh token в памяти и будет обновлять токен по refresh token. После перезапуска оно получает новый access token по password grant.
3. В TEAM-боте выполните `/crmprobe`. Команда показывает **только имена полей и типы** ответов. До сверки структуры не открывайте доступ клиентам и не включайте показ документов.
4. Сначала проверьте поиск заказа, идентификатор клиента и поле ИНН. Убедитесь, какое именно поле `inn_code` или `company_code` реально содержит ИНН организации.
5. Только после отдельной проверки групп документов задавайте `CLIENT_VISIBLE_DOC_GROUPS`. Запись в CRM оставьте выключенной (`CRM_ALLOW_WRITES=0`) до проверки конкретных операций.

## 6. Обновление

После push в подключённую ветку GitHub webhook синхронизирует репозиторий Amvera и запускает пересборку. Если webhook не настроен, обновите исходники через интерфейс Amvera и инициируйте сборку. Миграции выполняются при старте приложения.

## 7. Важные ограничения текущей версии

- Реализована основа обоих ботов, а не вся финальная система: в TEAM ещё нет рабочего процесса заявок, ставок, задач, пересчётов и аналитики; в CLIENT ещё нет чата с менеджером и загрузки документов. Смотрите таблицу этапов в README.
- Схемы ответов API 4logist в OpenAPI не описаны. Успешный OAuth ещё не подтверждает, что все поля и ответы CRM корректно распознаны.
- Авторизация клиента по номеру заказа и 4 цифрам ИНН — слабая схема. Для продакшена включайте подтверждение менеджером.
- `CRM_MODE=mock` не обращается к реальной CRM. Не используйте демонстрационные ответы как сведения о настоящих грузах.

## 8. Типичные ошибки

| Симптом | Причина / действие |
|---|---|
| `Не задан DATABASE_URL` | Добавьте PostgreSQL URL в переменные проекта |
| `Миграции не применены` | Проверьте host, порт, имя БД, логин, пароль и доступность кластера |
| `Telegram отверг токен` | Проверьте токен соответствующего бота; второй бот работает независимо |
| `terminated by other getUpdates` | Тот же бот запущен в другом экземпляре; оставьте только один polling-процесс |
| `CRM HTTP 401/403` | Проверьте OAuth-реквизиты, статус пользователя и его права в 4logist |
| `/crmprobe` возвращает неожиданные структуры | Передайте структуру полей разработчику; не включайте клиентские документы до подтверждения маппинга |
| Документы клиенту не показываются | Это безопасное поведение по умолчанию; сначала определите разрешённые группы |
